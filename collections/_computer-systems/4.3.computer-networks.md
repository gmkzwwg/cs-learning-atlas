# English

A network protocol specifies how participants exchange messages: their format, allowed order, and responses to loss, duplication, delay, or invalid input. Independent implementations can communicate when they agree on these rules. A useful first question is what one participant can conclude from the messages it has actually received.

The subject studies sharing links, finding paths, controlling load, and giving applications useful communication services despite failures. A packet may be delayed even when no component has failed; a timeout cannot distinguish every cause. These facts explain why reliability needs acknowledgments, state, and recovery policies rather than only faster links.

Layering separates recurring concerns: links carry frames, IP forwards packets across networks, transports provide communication services, and applications define message meaning. Stable interfaces allow implementations to change with less coupling. Performance, security, and middleboxes can still connect behavior across layers, so use the model to ask what each component guarantees rather than assuming complete independence.

Prerequisites include processes, buffers, and sockets (§4.2), graph algorithms (§2.6), and elementary probability. Some protocol work runs in kernels and some in user space. Begin by tracing one request through name resolution, transport setup, and application response before studying every protocol field.

## How the Internet Was Designed and What It Revealed About Networks

Packet switching addressed the economics of bursty communication. Circuit-switched systems reserve capacity along a connection, while packet networks let multiple conversations share links as packets arrive. Baran's work at RAND emphasized survivability; Davies's work at Britain's National Physical Laboratory emphasized efficient data communication. Packet switching can exploit alternative routes, but a failure can still disconnect the network or lose packets before routing recovers.

ARPANET began operating in 1969, connecting research sites including UCLA, SRI, UC Santa Barbara, and the University of Utah. Abbate's *Inventing the Internet*, explains that moving packets was only part of the work. Hosts needed interfaces and compatible protocols, and users needed useful applications. Resource sharing motivated the network, while applications such as email helped determine how it was actually used. This distinction between a working transport mechanism and a useful service remains relevant to system design.

Internetworking posed a further problem: independently administered networks differed in packet sizes, reliability, and internal design. Cerf and Kahn's work developed an architecture for communication across them. TCP and IP were separated as their roles became clearer, and ARPANET moved from NCP to TCP/IP in 1983. IP provides best-effort datagrams; endpoint transports can add ordering and recovery. NCP was a host protocol, so it should not be described as a routing protocol implemented by intermediate routers.

Saltzer, Reed, and Clark's end-to-end argument asks where a function can be completed correctly. A link checksum cannot by itself establish that an application stored the intended file: corruption or failure can occur elsewhere. Endpoints may need their own checks and acknowledgment of completion. Lower-layer reliability can still improve performance; the argument does not forbid every useful function inside the network. It identifies what a local guarantee is insufficient to establish.

DNS replaced distribution of a single host table with a delegated naming hierarchy. Different organizations could maintain their own zones, while caching reduced repeated queries. The Web, developed at CERN from 1989 onward, used the existing Internet to deliver linked documents and applications. Growth increased pressure on IPv4 addresses, leading to CIDR, NAT, and IPv6. NAT conserved addresses but complicated direct inbound connections; IPv6 expanded addressing without automatically resolving naming, routing, or security problems.

As the Internet connected less mutually trusted participants, missing authentication in foundational protocols became more consequential. DNSSEC adds signed DNS data, RPKI-based validation helps check route origins, and TLS protects communication between authenticated endpoints. They address different threats. A route-origin check does not validate every hop of a path, and an encrypted connection does not establish that the destination application behaves honestly.

QUIC, standardized in 2021, uses UDP to carry a transport with integrated cryptographic setup, congestion control, and multiple reliable streams. Loss on one stream need not delay delivery of available data on another, although streams share connection resources and congestion limits. HTTP/3 uses QUIC; HTTP/2 commonly uses TCP. [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000) explains the protocol's stream and connection model. The change illustrates how deployment constraints and application needs shape transport design.

## Routing, Reliability, and the Stack

Separate the questions answered at each layer: how to move a frame over one link, how to forward a datagram across networks, how to communicate between endpoints, and what an application message means. Successful delivery at one layer does not establish completion at every higher layer.

## The Network Layer: Addressing and Routing

IP provides a common packet format and forwarding abstraction across different link technologies. Its delivery is best effort: packets can be lost, delayed, duplicated, or reordered. Addressing and routing determine possible paths, while firewalls, reachability, and policy can prevent communication between otherwise connected hosts. Ethernet and Wi-Fi can carry IP without exposing all their implementation details to an application.

IP addresses identify network-layer endpoints or interfaces within an addressing context, rather than permanently identifying people or devices. Prefix aggregation lets routers keep routes for groups of addresses. Forwarding chooses a next hop for a packet; routing protocols help construct the information used by forwarding. CIDR supports variable-length prefixes. BGP exchanges reachability between autonomous systems and applies operator policies; an advertised route is not a guarantee that every destination will remain reachable or that the chosen path is shortest.

Within a routing domain, link-state protocols such as OSPF distribute topology information and compute paths; distance-vector approaches exchange reachability estimates with neighbors. Their convergence depends on topology, failure detection, protocol rules, and configuration. Different routers can temporarily disagree while updates propagate, causing loops or black holes. The distinction explains what information each router maintains, rather than giving a universal rule that one family is always faster or uses a fixed quadratic amount of memory.

## The Transport Layer: Reliability and Congestion Control

TCP provides an ordered byte stream with loss recovery and duplicate suppression while the connection remains usable. Sequence numbers identify byte positions; acknowledgments and retransmissions recover missing data. TCP preserves bytes, not application message boundaries: two sends can be received together, and one send can require several reads. An application must define its own framing, such as a length field or delimiter.

Flow control protects receiver capacity; congestion control limits pressure on the network. They solve different problems. Jacobson's work in the late 1980s helped address congestion collapse through endpoint control. Modern algorithms may use loss, delay, and explicit congestion notifications. A sender that retries aggressively can worsen congestion, so recovery and load control must work together.

Propagation delay also constrains throughput. To keep a 10 Mbit/s path busy with a 100 ms round-trip time, roughly 1 Mbit, or 125,000 bytes, must be in flight. This bandwidth-delay product explains why waiting for an acknowledgment after every small message can waste link capacity. Actual throughput also depends on windows, loss, receiver behavior, and competing traffic.

UDP carries datagrams without adding TCP-style reliable ordering or congestion control. Applications may tolerate loss or implement their own recovery, as QUIC does. They still need to avoid overwhelming the receiver or network. Choosing UDP is not automatically a latency optimization: the necessary reliability, security, and traffic control must be accounted for somewhere.

A TCP acknowledgment establishes receipt within the transport, not successful execution or durable storage by the remote application. If a server processes a request and its reply is lost, retrying can repeat the effect. Application acknowledgments, request identifiers, and duplicate handling address this ambiguity; §4.6 develops it as a distributed-systems problem.

## The Application Layer and Protocol Design

HTTP, DNS, SMTP, and SSH specify different application exchanges. TLS supplies protection for communication; its position and integration depend on the protocol stack, as the different designs of TCP-based HTTPS and QUIC illustrate. Studying message formats, state transitions, and error handling explains what a library call relies on.

TLS protects a connection's confidentiality and integrity and can authenticate its peer when credentials are validated correctly. TLS 1.3 normally supports a one-round-trip handshake; ephemeral key exchange provides forward secrecy, while PSK-only modes and early data need separate analysis. Its 0-RTT data can be replayed, so an application cannot treat every early request as safe to execute once. The [TLS 1.3 specification](https://www.rfc-editor.org/rfc/rfc8446) states these distinctions. Encryption also leaves some metadata visible and does not protect plaintext after a compromised endpoint receives it.

DNS separates authoritative data from recursive resolution and caching. On a cache miss, a resolver can follow referrals from the root through a top-level domain to the relevant authoritative server; cached answers or delegations can shorten that path. TTLs limit normal cache reuse but do not make every copy change simultaneously. DNSSEC authenticates signed data through a trust chain. DNS-over-TLS or DNS-over-HTTPS encrypts a particular client–resolver connection; the chosen resolver still sees the query, and encryption alone does not validate an authoritative answer.

Good protocol design requires specifying not just the successful case but every failure mode: what a client does when a server does not respond within the timeout, what a server does when it receives a request it cannot parse, how a half-open connection is cleaned up when one endpoint crashes. The RFCs that specify major Internet protocols devote substantial space to these edge cases, and implementations that fail to handle them correctly are a major source of security vulnerabilities and interoperability problems.

## What Studying This Changes

Computer networks changes what practitioners can see in distributed systems and in security.

The first change is the ability to reason about communication failures. A network call may fail because the request was lost, the response was lost, or the remote end crashed after receiving the request but before responding. These cases are not distinguishable from the caller's perspective. A distributed system that assumes network calls either succeed or fail cleanly will behave incorrectly when calls partially succeed — when a request is processed but the response is lost. Networks training instills the habit of reasoning about all failure modes, not just the happy path, and of designing protocols that behave correctly under partial failure.

Layering helps narrow a diagnostic question. Test whether an address resolves, whether a route exists, whether a transport connection can be established, whether peer authentication succeeds, and whether the application returns the expected response. A failure at one step suggests where to inspect next, but filters and proxies can act across layers. Record observations rather than treating a layer label as the diagnosis.

Protocol knowledge helps assess a security claim: what identity is authenticated, what fields are protected, and what information remains visible? DNSSEC, route-origin validation, and TLS address different properties. None alone establishes the authorization rules of an application or protects every aspect of a network path.

The fourth change is the ability to make informed protocol design decisions. Most practitioners design protocols in the broad sense regularly — defining the format and semantics of messages between services in a distributed system, specifying the behavior of APIs, designing the communication patterns of microservices. The discipline of protocol design — precise specification, failure-mode analysis, evolutionary design, careful tradeoff analysis — applies directly, and practitioners who have studied formal protocols bring more rigor to these informal protocol designs.

## Traps

| Trap | Why it misleads | Better response |
|---|---|---|
| Memorizing only the layer diagram | A layer name does not explain delivery, ordering, or failure behavior. | For each protocol, state its inputs, guarantees, and remaining responsibilities. |
| Memorizing every protocol field first | Details are easier to use after the underlying mechanism is understood. | Start with addressing, framing, acknowledgment, congestion, and authentication; consult specifications for details. |
| Treating an encrypted capture as plaintext | Packet capture does not automatically decrypt application content. | Inspect visible metadata and use controlled test sessions with supported key logging when studying encrypted payloads. |
| Confusing implementation behavior with a universal rule | Specifications allow choices, and implementations can contain extensions or bugs. | Compare the observed trace with the applicable protocol version and implementation documentation. |
| Equating transport security with authorization | An authenticated encrypted connection does not decide access to every application object. | Separate channel identity, message protection, and application permissions. |
| Assuming TCP acknowledgment means completed work | Acknowledged bytes may not yet have been processed or durably committed. | Design application replies and retry identifiers around the business operation. |

# 中文

网络协议规定参与者怎样交换消息，包括格式、允许的顺序，以及面对丢失、重复、延迟或无效输入时的处理。独立实现只有遵守相同规则，才能通信。一个有用的起点是：参与者能从实际收到的消息中得出什么结论？

这门学科研究共享链路、寻找路径、控制负载，以及在故障存在时向应用提供有用的通信服务。即使没有部件故障，数据包也可能延迟；超时无法区分每种原因。这解释了为什么可靠性需要确认、状态与恢复策略，而不只是更快的链路。

分层区分反复出现的问题：链路携带帧，IP 跨网络转发数据包，传输协议提供通信服务，应用定义消息含义。稳定接口减少实现变化带来的耦合，但性能、安全与中间设备仍可能连接不同层次的行为。因此，应利用模型询问每个组件保证什么，而不是假设完全独立。

先修知识包括进程、缓冲区和套接字（§4.2）、图算法（§2.6）以及初等概率。部分协议工作在内核中运行，部分在用户态运行。可以先跟踪一个请求怎样经过名称解析、传输连接建立和应用响应，再研究各协议字段。

## Internet 是如何被设计出来的，以及它揭示了什么网络问题

分组交换回应了突发通信的成本问题。电路交换系统沿连接预留容量，分组网络则让多路通信按数据包到达情况共享链路。Baran 在 RAND 的工作强调生存能力，Davies 在英国国家物理实验室的工作强调高效数据通信。分组交换可以利用替代路径，但故障仍然可能使网络断开，或在路由恢复前丢包。

ARPANET 于 1969 年开始运行，连接了 UCLA、SRI、UC Santa Barbara 和 University of Utah 等研究站点。Abbate 的 *Inventing the Internet* 说明，传送数据包只是工作的一部分。主机需要接口和兼容协议，用户需要有用的应用。资源共享推动了网络建设，而电子邮件等应用帮助决定了网络实际怎样被使用。工作正常的传输机制与有用服务之间的区别，今天仍与系统设计有关。

互联网络提出了进一步的问题：独立管理的网络具有不同的包大小、可靠性和内部设计。Cerf 与 Kahn 的工作发展了跨网络通信的架构。随着职责逐渐明确，TCP 与 IP 被分开；ARPANET 在 1983 年从 NCP 转向 TCP/IP。IP 提供尽力而为的数据报，端点传输协议可以增加排序与恢复。NCP 是主机协议，不应描述为中间路由器实现的路由协议。

Saltzer、Reed 与 Clark 的端到端论证，询问一项功能在哪里才能被正确完成。链路校验和本身不能建立应用已存下预期文件的结论，因为其他位置仍可能损坏或失败。端点可能需要自己的检查与完成确认。下层可靠性仍然可以改善性能；这个论证并不禁止网络内部的所有有用功能，而是指出局部保证不足以建立什么结论。

DNS 用分权的名称层次替代单一主机表的分发。不同组织可以维护自己的区域，缓存则减少重复查询。Web 从 1989 年起在 CERN 发展，利用已有互联网交付相互链接的文档与应用。增长增加了 IPv4 地址压力，推动 CIDR、NAT 与 IPv6。NAT 节约地址，却使直接入站连接更复杂；IPv6 扩展地址空间，但不会自动解决命名、路由或安全问题。

随着互联网连接越来越多互不信任的参与者，基础协议缺少认证的后果更加明显。DNSSEC 增加签名 DNS 数据，基于 RPKI 的验证帮助检查路由来源，TLS 保护经认证端点之间的通信。三者针对不同威胁。路由来源检查不会验证路径上的每一跳，加密连接也不证明目标应用诚实运行。

2021 年标准化的 QUIC 使用 UDP 承载传输协议，集成密码协商、拥塞控制与多条可靠流。一条流上的丢失，不必延迟另一条流中已有数据的交付，不过各流仍共享连接资源和拥塞限制。HTTP/3 使用 QUIC，HTTP/2 通常使用 TCP。[RFC 9000](https://www.rfc-editor.org/rfc/rfc9000)解释了流与连接模型。这种变化说明，部署约束与应用需要怎样影响传输设计。

## 路由、可靠性与协议栈

分开看待各层回答的问题：怎样在一条链路上传送帧，怎样跨网络转发数据报，怎样在端点之间通信，以及应用消息意味着什么。某一层交付成功，不建立每个更高层都已完成工作的结论。

## Network Layer：寻址与路由

IP 在不同链路技术之上提供共同的数据包格式与转发抽象。交付尽力而为，数据包可能丢失、延迟、重复或乱序。寻址与路由确定可能路径，防火墙、可达性与策略则可能阻止已连接主机之间的通信。以太网与 Wi-Fi 都可以承载 IP，而不把全部实现细节暴露给应用。

IP 地址在特定寻址环境中标识网络层端点或接口，并非永久标识人或设备。前缀聚合让路由器为一组地址保存路由。转发为数据包选择下一跳，路由协议帮助形成转发使用的信息。CIDR 支持可变长度前缀。BGP 在自治系统之间交换可达信息，并应用运营者策略；通告一条路由，不保证每个目标始终可达，也不保证选中路径最短。

在路由域内，OSPF 等链路状态协议分发拓扑信息并计算路径；距离向量方法则与邻居交换可达性估计。收敛取决于拓扑、故障检测、协议规则与配置。更新传播期间，不同路由器可能暂时不一致，造成环路或黑洞。这个区别说明每个路由器维护什么信息，并不提供某一类总是更快或必然使用固定平方内存的通用规则。

## Transport Layer：可靠性与拥塞控制

只要连接仍可使用，TCP 就提供带丢失恢复与重复抑制的有序字节流。序号标识字节位置，确认与重传恢复缺失数据。TCP 保留字节，不保留应用消息边界：两次发送可能一起被接收，一次发送也可能需要多次读取。应用必须定义自己的分帧方式，例如长度字段或分隔符。

流量控制保护接收端容量，拥塞控制限制对网络的压力，二者解决不同问题。Jacobson 在八十年代末的工作通过端点控制帮助应对拥塞崩溃。现代算法可以使用丢失、延迟和显式拥塞通知。过于积极的重试会加重拥塞，因此恢复与负载控制必须配合。

传播延迟也限制吞吐量。要使一条 10 Mbit/s、往返时间 100 ms 的路径保持忙碌，需要大约 1 Mbit，即 125,000 字节的数据在途。这个带宽时延积解释了为什么每发送一条小消息就等待确认，可能浪费链路容量。实际吞吐量还取决于窗口、丢失、接收端行为和竞争流量。

UDP 传送数据报，不增加 TCP 式的可靠排序或拥塞控制。应用可以容忍丢失，或像 QUIC 那样自行实现恢复，但仍需避免压垮接收端或网络。选择 UDP 不自动等于优化延迟，所需可靠性、安全性与流量控制总要在某处实现。

TCP 确认表示传输层收到数据，不表示远程应用已成功执行操作或持久保存结果。如果服务器处理了请求而回复丢失，重试可能重复产生效果。应用确认、请求标识与去重处理解决这种歧义；§4.6 会将其作为分布式系统问题展开。

## Application Layer 与协议设计

HTTP、DNS、SMTP 与 SSH 规定不同的应用交换。TLS 提供通信保护，其位置与整合方式依赖协议栈，基于 TCP 的 HTTPS 与 QUIC 的不同设计说明了这一点。研究消息格式、状态转换与错误处理，可以解释一次库调用依赖什么。

在正确验证凭据时，TLS 保护连接的机密性与完整性，并可认证通信对端。TLS 1.3 通常支持一轮往返握手，临时密钥交换提供前向保密；仅使用预共享密钥的模式和早期数据需要单独分析。0-RTT 数据可能被重放，因此应用不能认为每个早期请求都可安全地只执行一次。[TLS 1.3 规范](https://www.rfc-editor.org/rfc/rfc8446)说明了这些区别。加密仍会暴露部分元数据，也不能保护被攻陷端点收到之后的明文。

DNS 区分权威数据、递归解析与缓存。缓存未命中时，解析器可以从根开始，经顶级域的指引找到相关权威服务器；缓存的答案或委派信息可以缩短路径。TTL 限制通常的缓存复用时间，却不会使每个副本同时改变。DNSSEC 通过信任链认证签名数据。DNS-over-TLS 或 DNS-over-HTTPS 加密特定的客户端—解析器连接，所选解析器仍能看到查询，而且仅加密连接并不验证权威答案。

好的协议设计不只规定成功情况，还必须规定每种失败模式：当 server 在 timeout 内不响应时，client 做什么；当 server 收到一个无法解析的 request 时，server 做什么；当一个 endpoint 崩溃后，half-open connection 如何被清理。规定主要 Internet protocols 的 RFCs 会把大量篇幅用于这些边缘情况，而不能正确处理它们的实现，是安全漏洞和互操作性问题的主要来源。

## 学习这一部分会改变什么

计算机网络会改变实践者在分布式系统和安全中能够看见什么。

第一个变化，是能够推理通信失败。一次 network call 可能失败，是因为 request 丢失了，response 丢失了，或者远端在收到 request 后、回复前崩溃了。从调用者角度看，这些情况无法区分。一个假设 network calls 要么成功、要么干净失败的分布式系统，会在 partial success 时行为错误——也就是 request 已被处理，但 response 丢失。网络训练会建立一种习惯：推理所有失败模式，而不只是 happy path，并设计在 partial failure 下仍能正确行为的协议。

分层帮助缩小诊断问题：地址是否能解析，路由是否存在，传输连接能否建立，对端认证是否成功，以及应用是否返回预期响应。某一步失败会提示下一步检查的位置，但过滤器与代理也可能跨层工作。应记录观察结果，而不把层次标签本身当成诊断结论。

协议知识帮助评估安全主张：认证了什么身份，保护了哪些字段，还有哪些信息可见？DNSSEC、路由源验证与 TLS 处理不同性质。任何一种都不会单独建立应用授权规则，或保护网络路径的每个方面。

第四个变化，是能够做出有依据的协议设计决策。多数实践者其实经常在广义上设计协议——定义分布式系统中服务之间的消息格式和语义，规定 API 行为，设计 microservices 的通信模式。协议设计纪律——精确规约、失败模式分析、演化式设计、谨慎权衡分析——可以直接应用，而学习过正式协议的实践者，会把更多严谨性带入这些非正式协议设计中。

## 资源

**书籍与文本**

Kurose 与 Ross 的 **Computer Networking: A Top-Down Approach** 从应用出发展开支撑协议。Peterson 与 Davie 的 **Computer Networks: A Systems Approach** 强调系统设计。Fall 与 Stevens 的 **TCP/IP Illustrated, Volume 1** 第二版研究数据包层行为。历史协议描述应与适用规范对照阅读：RFC 9293 整合了始于 RFC 793 的 TCP 规范，TLS 1.3 与 QUIC 则各有规范。

## 陷阱

| 误区 | 为什么会误导 | 更好的做法 |
|---|---|---|
| 只记分层图 | 层次名称不解释交付、排序或失败行为。 | 对每个协议说明输入、保证与剩余责任。 |
| 先背诵所有协议字段 | 理解基础机制后，细节才更容易使用。 | 先学习寻址、消息定界、确认、拥塞与认证，再查规范中的细节。 |
| 把加密抓包当作明文 | 抓包不会自动解密应用内容。 | 先检查可见元数据；研究加密载荷时，使用支持密钥日志的受控测试会话。 |
| 把实现行为当作普遍规则 | 规范允许选择，实现也可能包含扩展或错误。 | 把观察到的追踪与适用协议版本、实现文档比较。 |
| 把传输安全等同于授权 | 经过认证的加密连接，不决定每个应用对象的访问权。 | 分开考虑连接身份、消息保护与应用权限。 |
| 假设 TCP 确认意味着工作完成 | 已确认的字节可能尚未处理或持久提交。 | 围绕业务操作设计应用回复与重试标识。 |
