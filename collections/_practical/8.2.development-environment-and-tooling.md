# English

A development environment connects a question about a program to a way of checking it: locate a definition, change an expression, run a test, inspect a value, and compare the result. Tool fluency matters because these operations recur throughout development. Its value depends on whether it makes feedback faster and more reliable, not on the number of tools installed.

Learn a small complete workflow first: obtain the project, install its declared dependencies, build it, run one test, and reproduce those steps from the command line. Editor integration is useful, but knowing the underlying commands helps explain differences between your machine and continuous integration (§7.4).

*Prerequisites and connections: Basic programming (§2.1). Processes, files, and permissions (§4.2) help explain what development tools do.*

## The Shape of the Skill: Shortening the Feedback Cycle

Development tools reduce the amount of machine bookkeeping a programmer must perform. Assemblers replaced numeric addresses with symbolic names; reusable subroutines reduced repeated implementation; interactive editors shortened the cycle between a change and its result. The histories of EDSAC and Unix show that programming environments developed alongside programs, rather than being optional conveniences added after programming was understood.

Unix made a particularly useful design choice: many programs could exchange data through standard input and output, while the shell arranged their execution. This allowed a new task to be expressed as a composition of existing tools. Integrated environments take a complementary approach by bringing editing, navigation, building, and debugging into a shared interface. Both approaches depend on clear interfaces between operations.

The practical test for an improvement is local. If finding a definition interrupts your work repeatedly, learn semantic navigation. If installing dependencies fails on a colleague's machine, make the setup explicit. Configuration also has a maintenance cost: a large collection of plugins can introduce conflicts and hidden assumptions. Prefer a setup you can explain and restore.

## The Shell, the Editor, and the Build System

## The Shell as a Composable Toolkit

The shell starts programs, passes arguments, connects streams, and reports exit status. Quoting and expansion happen before a program receives its arguments. A path containing spaces must remain one argument; a list of filenames is not safely represented by arbitrary whitespace. These rules explain many failures that otherwise look like mysterious command behavior.

For a concrete pipeline, suppose each line of a single log file contains exactly a severity and an error code separated by whitespace, such as `ERROR E42`. Then `awk '$1 == "ERROR" {print $2}' 'service log.txt' | sort | uniq -c | sort -nr` counts each error code and orders counts from largest to smallest. Each stage has a distinct job. Sorting before counting matters because `uniq` groups adjacent equal lines. The quoted filename remains one argument.

This command assumes a particular record format. It does not parse arbitrary JSON or multiline stack traces; use a parser appropriate to those formats. Inspect intermediate output on a small sample before trusting a pipeline. In Bash, a pipeline normally reports the last command's exit status; `set -o pipefail` makes a failure in an earlier stage affect that status too. Output and successful execution are separate things to check.

Search tools also have scope. For example, `rg` normally skips ignored and hidden files. No search result may mean the name is absent, the search scope is wrong, or the name is constructed at runtime. Read the relevant options instead of treating a search as an exhaustive proof.

## The Editor or IDE as a Navigation and Feedback Tool

An editor's most useful features help you navigate and change the program's structure: jump to definition, find references, inspect types, rename a symbol, run a focused test, and stop at a breakpoint. A language server supplies language-specific analysis to an editor through a common protocol; the quality and completeness of that analysis depend on the server and the project configuration.

Semantic renaming is usually more precise than replacing matching text. It can distinguish two local variables with the same spelling. It may still miss names embedded in configuration, reflection, templates, or external callers. Review the resulting diff and test the affected behavior.

Configure formatting and diagnostics to agree with the repository. Learn a few frequently used operations until they are easy to invoke. The choice between a terminal editor and an IDE matters less than being able to follow a value, inspect a change, and reproduce a failure without losing your place.

## Build Systems and Package Management

A build system describes how outputs depend on inputs. If two source files include the same header, changing that header may require recompiling both before linking. An omitted dependency can leave an old output in place even though a clean build succeeds. Incremental building is therefore a correctness problem as well as a speed optimization.

Caching extends the same idea: reuse an output when all inputs that affect it are unchanged. Compiler version, flags, generated files, and environment variables may be inputs too. A build that reads an undeclared local file or fetches changing network content can produce different results from apparently identical source. Hermetic builds try to control such dependencies; reproducible builds require the specified inputs and environment to yield identical output artifacts. Neither property follows merely from choosing a modern build tool.

Package manifests describe dependencies; lockfiles record a resolved selection in a tool-specific format. A lockfile helps repeat installation, but does not by itself fix the operating system, compiler, external services, or every build input. Version numbers express a maintainer's compatibility policy, not a proof that your use remains compatible. Test dependency updates and keep setup instructions alongside the project.

## AI-Assisted Development as Part of the Toolchain

AI assistance can suggest commands, explain diagnostics, or prepare changes. Give it the actual language version, relevant files, and expected behavior. Check proposed commands for their working directory, inputs, and effects before running them; a plausible command can target the wrong files or rely on options your installed tool lacks.

Evaluate assistance across the whole task: time to explain the problem, inspect the proposal, test it, and correct mistakes. Faster text generation is only one part of that cost. A useful workflow keeps changes small enough to inspect and preserves the commands and evidence needed to reproduce the result.

## What Changes With Mastery

You can explain what happens between editing source and running the resulting program, and diagnose which step failed. You also know when a search, cache, or diagnostic has incomplete information.

As an exercise, set up a small project in a fresh directory using only its written instructions. Build it, run a test, change a dependency input, and confirm that the relevant output updates. Every undocumented manual step you discover is an opportunity to make the environment easier for the next person to use.

Automation can preserve a repeated procedure as well as save keystrokes. Turn a stable sequence into a script with explicit inputs and a meaningful failure status, then keep it with the project when others need it. Automating an operation you do not yet understand can instead repeat a mistake more efficiently; first make the manual procedure explainable and checkable.

## Traps

| Trap | Why it misleads | Better response |
|---|---|---|
| Collecting tools without a task | Configuration has learning and maintenance costs. | Improve a recurring operation and evaluate the result. |
| Pasting an unexplained pipeline | Quoting, record formats, and exit status affect correctness. | Inspect arguments and intermediate output on a small sample. |
| Treating search or rename as exhaustive | Ignored files and dynamic references can be missed. | Check scope and review affected behavior. |
| Equating a lockfile with reproducibility | Other inputs and the toolchain can still vary. | Record and control the inputs that affect the build. |
| Measuring assistance by generated output | Review and correction can dominate the task. | Measure time to a checked, reproducible result. |

# 中文

开发环境把关于程序的问题与检查方法连接起来：找到定义、修改表达式、运行测试、观察数值，再比较结果。这些操作贯穿开发过程，因此熟练使用工具很有价值。价值在于能否更快、更可靠地得到反馈，而不在于安装了多少工具。

先掌握一个完整的小流程：获取项目、安装声明的依赖、构建、运行一个测试，再从命令行复现这些步骤。编辑器集成很方便，但理解底层命令，有助于解释本机与持续集成环境之间的差异（§7.4）。

*前置知识与联系：基础编程（§2.1）。进程、文件和权限（§4.2）有助于解释开发工具的行为。*

## 技能的构成：缩短反馈过程

开发工具减少了程序员必须手工处理的机器细节。汇编器用符号名称代替数值地址；可复用子程序减少了重复实现；交互式编辑器缩短了修改到观察结果的过程。EDSAC 和 Unix 的历史表明，编程环境与程序共同发展，并不是掌握编程之后才添加的便利设施。

Unix 的一个实用设计是让许多程序通过标准输入、标准输出交换数据，由 shell 安排执行。这样，新任务可以通过组合已有工具来完成。集成开发环境采用互补的方式，把编辑、导航、构建和调试放在同一界面里。两种方式都依赖操作之间清楚的接口。

改进是否值得，应根据实际问题判断。查找定义经常打断工作，就学习语义导航；同事安装依赖总失败，就把安装条件写清楚。配置本身也有维护成本：大量插件可能引入冲突和隐含假设。选择自己能够解释和恢复的环境。

## Shell、编辑器与构建系统

## Shell 作为可组合工具箱

Shell 启动程序、传递参数、连接数据流，并报告退出状态。程序收到参数之前，shell 已经处理了引号和展开规则。含空格的路径必须保持为一个参数；不能随便用空白字符分隔来表示文件名列表。理解这些规则，就能解释许多看似莫名其妙的命令故障。

例如，假设一个日志文件的每行恰好包含由空白分隔的严重程度和错误码，如 `ERROR E42`。那么 `awk '$1 == "ERROR" {print $2}' 'service log.txt' | sort | uniq -c | sort -nr` 会统计各错误码，并按次数从多到少排列。每一步都有明确职责。必须先排序再计数，因为 `uniq` 合并的是相邻的相同行。加引号的文件名保持为一个参数。

这条命令依赖特定的记录格式，不能解析任意 JSON 或多行堆栈信息；这些数据需要相应的解析器。先用小样本检查中间结果，再依赖整条流水线。在 Bash 中，流水线通常报告最后一条命令的退出状态；`set -o pipefail` 让前面步骤的失败也影响这一状态。输出是否正确与执行是否成功，需要分别检查。

搜索工具也有范围。例如，`rg` 通常跳过被忽略的文件和隐藏文件。没有搜索结果，可能意味着名称不存在、搜索范围不对，或名称在运行时才构造出来。应查阅相关选项，不能把一次搜索当作穷尽所有可能的证明。

## 把编辑器或 IDE 用作导航与反馈工具

编辑器中实用的功能，可以帮助你理解和修改程序结构：跳转到定义、查找引用、查看类型、重命名符号、运行针对性测试，以及在断点暂停。语言服务器通过通用协议向编辑器提供特定语言的分析；分析的质量和完整性取决于服务器及项目配置。

语义重命名通常比替换匹配文本更准确，例如能够区分拼写相同的两个局部变量。但它仍可能漏掉配置、反射、模板或外部调用者中的名称。应检查生成的差异，并测试受影响的行为。

让格式化与诊断配置符合仓库约定。把几个经常使用的操作练熟即可。终端编辑器与 IDE 的选择，通常不如以下能力重要：追踪一个值、检查一次修改，以及在不丢失当前上下文的情况下复现故障。

## 构建系统与包管理

构建系统描述输出怎样依赖输入。如果两个源文件都包含同一个头文件，修改头文件后，可能需要重新编译两者再链接。漏写依赖，会使旧产物继续被使用，即使从头构建能够成功。因此，增量构建既涉及速度，也涉及正确性。

缓存扩展了同一个思路：所有影响结果的输入都未变化时，就复用输出。编译器版本、参数、生成文件和环境变量，也可能是输入。如果构建读取未声明的本机文件，或下载不断变化的网络内容，看似相同的源代码就可能产生不同结果。封闭构建尝试控制这些依赖；可复现构建要求指定的输入与环境产生相同的输出产物。选用现代构建工具，本身不保证这两种性质。

依赖清单描述需要哪些依赖；锁文件以特定工具的格式记录解析出的版本组合。锁文件有助于重复安装，但单凭它不能固定操作系统、编译器、外部服务或全部构建输入。版本号表达维护者的兼容性约定，不能证明你的具体用法仍然兼容。更新依赖后应测试，并将环境配置说明保存在项目中。

## AI 辅助开发作为工具链的一部分

AI 可以建议命令、解释诊断信息或准备修改。应提供实际使用的语言版本、相关文件和预期行为。执行建议命令前，检查工作目录、输入和影响；看似合理的命令，可能操作错误的文件，或依赖本机工具并不支持的选项。

评价辅助效果时，要考虑整个任务：解释问题、检查建议、测试和纠错分别需要多少时间。更快生成文本只是其中一部分。实用的流程应让改动小到能够检查，并保留复现结果所需的命令与证据。

## 熟练之后会发生什么变化

你能够解释从编辑源代码到运行程序之间发生了什么，并判断哪一步失败了；也知道搜索、缓存或诊断何时只掌握了部分信息。

可以做一个练习：仅根据书面说明，在新目录中配置一个小项目。构建、运行测试、修改一个依赖输入，再确认相关输出确实更新。每发现一个未记录的手工步骤，就有机会让下一个使用者更容易配置环境。

自动化不仅减少按键，也能保存一个反复执行的流程。把稳定步骤写成输入明确、失败状态有意义的脚本；别人也需要时，就把它保存在项目中。自动化尚未理解的操作，反而可能更高效地重复错误；应先让手工流程能够被解释和检查。
